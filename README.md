# mdmis-backend

FastAPI backend for MDMIS (Mineral Detection & Mining Intelligence System),
targeting Neon (serverless Postgres). Async throughout: SQLAlchemy 2.0 async
ORM, asyncpg driver, Alembic migrations.

## Apps

- `accounts` — Organisation + custom User model (10 SRS roles), JWT auth (register/login/refresh/me)
- `sites` — mining sites/concessions
- `scans` — ScanSession, MineralZone
- `traceability` — MineralBatch (auto-generated chain-of-custody id), CustodyEvent (immutable)
- `safety` — SafetyIncident (+ acknowledge action)
- `transport` — Shipment
- `compliance` — ComplianceReport

All client-data models carry an `organisation_id` and every query is scoped
to it via `app.crud.org_scoped_crud_router` — one org can never read or
write another org's records (`system_admin` is the only exception).

## Setup

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r requirements.txt
copy .env.example .env        # fill in DATABASE_URL (Neon connection string)
python -m alembic upgrade head
python -m app.seed            # creates demo org, 4 demo users, 10 sites
python -m uvicorn app.main:app --reload
```

Without a `DATABASE_URL` set, it falls back to a local SQLite file
(`db.sqlite3`) so the project runs out of the box. A plain `postgresql://`
Neon connection string works as-is — it's rewritten to
`postgresql+asyncpg://` automatically, and `sslmode=require` is translated
into the asyncpg SSL connect arg.

## Migrations

```bash
python -m alembic revision --autogenerate -m "describe the change"
python -m alembic upgrade head
```

Note: autogenerated migrations reference the custom `GUID` type
(`app.types.GUID`) used for every UUID primary/foreign key — the import is
already wired into `alembic/script.py.mako`, so new migrations pick it up
automatically.

## 3D block terrain

The map's 3D subsurface block draws each site's ground surface from
`GET /api/sites/{id}/terrain`, which serves the `site_terrains` table.
The terrain itself is produced by mdmis-ml-service
(`scripts/ingest_terrain.py`, Copernicus DEM or a drone survey) and loaded
here with:

```bash
python -m app.import_terrain --dir ../mdmis-ml-service/data/terrain
```

Run it once per database: locally, and against the deployed database
(set `DATABASE_URL` to it for that one command) after
`alembic upgrade head`. A site with no stored terrain falls back to asking
the ML service at `ML_SERVICE_URL`, and if that isn't reachable either,
the route returns 404 and the frontend uses a public elevation API.

## Preparing external datasets

Datasets downloaded from Kaggle, open-data portals or survey exports usually
carry extra columns, other units and bad rows. `tools/prepare_dataset.py`
filters them down to exactly what MDMIS ingests — deterministically, with a
reason for every dropped row:

```bash
pip install -r requirements-dev.txt          # pandas + openpyxl (dev only)
python tools/prepare_dataset.py --list-targets
python tools/prepare_dataset.py survey.csv --target magnetometer
python tools/prepare_dataset.py assays.xlsx --target lab --region none
python tools/prepare_dataset.py data.csv --target gamma --map th_ppm=eTh_value
```

Targets: `magnetometer`, `gamma`, `em`, `lab` (element ppm, converts ppb/%
and oxide grades such as SnO2 / Ta2O5 / WO3 / Li2O), `occurrences` (keeps only
minerals MDMIS tracks), `gas` and `geotechnical` (also writes ready-to-POST
`/api/ingest/readings` JSON). Points outside Rwanda are dropped unless
`--region none` or a custom `min_lat,min_lon,max_lat,max_lon` is given.

Each run writes `<name>.mdmis-<target>.csv` (upload it on Sensor Data →
Path 1), `<name>.rejected.csv` (every dropped row + reason) and
`<name>.report.json` (column mapping, conversions, counts per rule).

## Security model

**Organisations are isolated.** Every read is scoped to the caller's
organisation (system_admin sees all). Every write that points at another
record (a site, scan session, batch, zone) is checked to belong to the
caller's organisation too: otherwise 404, same as "doesn't exist".

**Who may change what** (`app/authz.py`, mirroring the frontend's
`lib/rbac.ts`; system_admin may do everything, every role may read):

| Action | Roles |
|---|---|
| Create/edit sites | org_admin, geologist, mine_manager |
| Create/edit scan sessions and mineral zones, classify | org_admin, geologist, mine_manager |
| Mark a zone `lab_confirmed` (ML training ground truth) | org_admin, geologist |
| Create/edit mineral batches, record custody events | org_admin, mine_manager |
| Set a batch's compliance verdict (`compliant`, `compliance_note`) | org_admin, compliance_manager |
| Create/edit compliance reports | org_admin, compliance_manager |
| Report a safety incident | everyone |
| Edit safety incidents, safety rules, transport, devices | org_admin, mine_manager |
| Delete anything | org_admin |

Enum-like fields (minerals, statuses, frameworks, incident types) only
accept the values in each app's `models.py`.

**Sign-in.** 5 wrong passwords pause an account for 15 minutes. Code
emails (verification, reset) are capped at 3 per address per 15 minutes.
A code only completes sign-up for an unverified account; a verified
account that forgot its password uses `POST /auth/forgot-password/` then
`/auth/reset-password/` (which also lets the real owner reclaim an
address someone else registered first). Rate limits live in memory
(`app/ratelimit.py`), which fits the single Render instance.

**Ending sessions.** Tokens carry the user's `token_version`. A password
change or reset, or `POST /auth/logout/` (signs out every device), bumps
it and every older token stops working.

**Deployment settings.** The app refuses to start against a real
database if `SECRET_KEY` is a published placeholder, and service-key
endpoints stay closed while `ML_SERVICE_API_KEY` is one. API docs are off
in production (`API_DOCS_ENABLED=true` to override). Only organisations
listed in `TRAINING_ORG_IDS` feed `GET /scans/retrain-data`.

Regression check: `python tests/test_security.py` replays the
2026-11-12 audit's attacks against a throwaway database (all PASS).
